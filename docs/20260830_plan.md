## 1. Context

`dotnet build src/DayDash.slnx` is green today, but green means *compiles*, not *works*. The solution is a skeleton:

- `DayDashDbContext` has **no `DbSet`s, no `OnModelCreating`, no entity configuration**. There are no migrations, nothing calls `Migrate()`/`EnsureCreated()`, and the SQLite file is never created. Every repository call would throw at runtime.
- `CalendarMonthView.BuildMonthGrid()` is an empty method body; `CalendarWeekView` builds 7 day models and never populates `Events`; `EventListComponent`/`EventDetailComponent` are correct but referenced by no parent.
- `StudyPlannerService.GetSubjectConfigsAsync` returns `SubjectConfig.DefaultSubjects` (a fresh in-memory list, new `Guid`s every call); `SaveSubjectConfigAsync` only calls `_logger.LogInformation`.
- `MauiCameraService` captures a photo and returns `string.Empty` (`// TODO ML Kit`). `MauiReminderService` is five no-ops. The three `AppWidgetProvider`s write literal `"Today's Events"` into their `RemoteViews`.
- `DayDash.Web` is an untouched Blazor WASM template with **zero** `ProjectReference`s.
- Localization is half-wired: `CalendarComponent` reads `MonthView`/`WeekView`, `SubjectConfigComponent` reads `MinutesPerGoal`/`NewSubject` — **none of these four keys exist**; `CalendarResources.Designer.cs` is stale; `AppShell.xaml` and every `*Page.xaml` carry hardcoded English titles.

The job: turn every module into a working, offline, localized feature on Android, with `DayDash.Web` as a browser preview of the same components, using MiniMate's architecture and look-and-feel — in **8 vertical slices** (Slice 0 = scaffolding, Slices 1–7 = the requirement's slices). Each slice ends with:

```
dotnet build src/DayDash.slnx        -> 0 errors
dotnet test  tests/DayDash.Tests/... -> all green
code review performed and addressed
```

**Deliberate re-ordering vs. the requirement doc** (sanctioned by "parity/i18n last *or interleaved*"): the shared shell (router, `MainLayout`, `NavMenu`, global CSS, host page wrappers) is pulled **forward into Slice 0**, because every feature slice needs a place to render and a way to be looked at in the browser. Slice 7 then becomes what it should be — the *audit* slice: live culture switching end-to-end, zero-hardcoded-strings sweep, resx completeness, MAUI/Web parity verification.

**Two premises from the brief corrected during research:**
- No `bin/`/`obj/` artifacts are tracked (`git ls-files | grep -c "/obj/\|/bin/"` = 0); `.gitignore` already covers them. What is pending is the 124-entry staged working tree (the root->`src/` move) — commit that first in Slice 0.
- NU1903 root cause is `SQLitePCLRaw.lib.e_sqlite3` 2.1.11 (GHSA-2m69-gcr7-jv3q) via `Microsoft.EntityFrameworkCore.Sqlite` in Storage, leaking into all 5 module RCLs. `dotnet-ef` is not installed.

## 2. Architecture Decisions

### AD-1 — Circular dependency: `IModelConfiguration` + `IDataSeeder` contributed by feature modules; migrations in a new `DayDash.Migrations` project

`DayDash.Modules.Storage/Application/Contracts/IModelConfiguration.cs`:

```csharp
public interface IModelConfiguration
{
    void Apply(ModelBuilder modelBuilder);
}
```

Each entity-owning module ships **one** `IModelConfiguration` in `Infrastructure/Persistence/` that applies its own standard `IEntityTypeConfiguration<T>` classes:

```csharp
// src/Modules/DayDash.Modules.Calendar/Infrastructure/Persistence/CalendarModelConfiguration.cs
public sealed class CalendarModelConfiguration : IModelConfiguration
{
    public void Apply(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfiguration(new CalendarEventConfiguration());
        modelBuilder.ApplyConfiguration(new EventTypeConfigConfiguration());
    }
}
```

`DayDashDbContext` takes them via constructor injection and applies them in `OnModelCreating`:

```csharp
public class DayDashDbContext(
    DbContextOptions<DayDashDbContext> options,
    IEnumerable<IModelConfiguration> modelConfigurations) : DbContext(options)
{
    private readonly IEnumerable<IModelConfiguration> _modelConfigurations = modelConfigurations;

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        base.OnModelCreating(modelBuilder);
        foreach (var configuration in _modelConfigurations)
            configuration.Apply(modelBuilder);
    }
}
```

*Why a non-generic `IModelConfiguration` and not `IEnumerable<IEntityTypeConfiguration<T>>` directly?* DI cannot resolve an open-generic collection whose `T` is unknown at the injection site; a non-generic collector is required either way. The per-entity classes stay idiomatic `IEntityTypeConfiguration<T>`.

`AddDbContext<T>` resolves extra constructor parameters from the container, so the DI path needs no special wiring. The two **non-DI** construction sites (design-time `dotnet ef`, Android widget) go through one shared factory (AD-7 / `DayDash.Migrations`).

**Seeding is symmetric.** Storage owns orchestration, modules own their data:

```csharp
// Storage/Application/Contracts/IDataSeeder.cs
public interface IDataSeeder { int Order { get; } Task SeedAsync(DayDashDbContext context, CancellationToken ct = default); }
// Storage/Application/Contracts/IDatabaseInitializer.cs
public interface IDatabaseInitializer { Task InitializeAsync(CancellationToken ct = default); }
```

`DatabaseInitializer` runs `Database.Migrate()` (SQLite) or `Database.EnsureCreated()` (InMemory), then all `IDataSeeder`s ordered by `Order`. Each seeder is a **no-op when its table is non-empty** (`if (await context.Set<T>().AnyAsync(ct)) return;`). Calendar ships `EventTypeSeeder` (Order 10), StudyPlanner `SubjectConfigSeeder` (20), Reminder `ReminderConfigSeeder` (30). Remove a module -> its model config *and* seed data disappear (NFR3).

**New project `src/DayDash.Migrations/DayDash.Migrations.csproj`** (`Microsoft.NET.Sdk`, `net10.0`):

| ProjectReference | Reason |
|---|---|
| `DayDash.Modules.Storage` | `DayDashDbContext`, `IModelConfiguration` |
| `DayDash.Modules.Calendar` | `CalendarModelConfiguration` |
| `DayDash.Modules.StudyPlanner` | `StudyPlannerModelConfiguration` |
| `DayDash.Modules.Reminder` | `ReminderModelConfiguration` |

PackageReferences: `Microsoft.EntityFrameworkCore.Sqlite`, `Microsoft.EntityFrameworkCore.Design`.

Contents:
- `DayDashModelConfigurations.cs` — `public static IReadOnlyList<IModelConfiguration> All { get; } = [new CalendarModelConfiguration(), new StudyPlannerModelConfiguration(), new ReminderModelConfiguration()];`
- `DayDashDbContextFactory.cs` — `public static DayDashDbContext CreateSqlite(string databasePath, bool readOnly = false)`; builds options with `.UseSqlite(cs, b => b.MigrationsAssembly(MigrationsAssemblyName))` and returns `new DayDashDbContext(options, DayDashModelConfigurations.All)`.

**Migrations live in `DayDash.Migrations`, not in Storage** — a snapshot in Storage stops compiling the moment any module adds an enum or module-owned value-object property. A dedicated migrations assembly removes that landmine and self-documents where `dotnet ef` must point.

`AddDayDashStorage` gets three overloads so Storage never names a provider:


All three also register `IRepository<>`->`BaseRepository<>` (scoped), `IDatabaseInitializer`->`DatabaseInitializer` (scoped) and `IDataChangeNotifier`->`DataChangeNotifier` (scoped).

**Bonus cleanup**: `Microsoft.EntityFrameworkCore.Sqlite` moves **out** of `DayDash.Modules.Storage.csproj` into `DayDash.Migrations` + `DayDash.Maui` only. Storage keeps provider-agnostic `Microsoft.EntityFrameworkCore`. This removes the vulnerable native SQLite binary from all five module RCLs (AD-6).

### AD-2 — `DateOnly`/`TimeOnly`: native EF Core 10 support, no value converters; all date filters become half-open ranges

No `ValueConverter`s. EF Core 10's SQLite provider maps `DateOnly`->`TEXT 'yyyy-MM-dd'` and `TimeOnly`->`TEXT 'HH:mm:ss.fffffff'`; both sort/compare correctly as lexicographic TEXT, and `==`/`>=`/`<` translate. EF InMemory needs nothing.

Rewrite every date filter as a **half-open range**:

```csharp
// CalendarRepository.GetByMonthAsync — replace e.Date.Year == year && e.Date.Month == month
var first = new DateOnly(year, month, 1);
var next  = first.AddMonths(1);
return await _context.Set<CalendarEvent>()
    .Where(e => e.Date >= first && e.Date < next)
    .OrderBy(e => e.Date).ThenBy(e => e.TimeFrom)
    .ToListAsync(ct);
```

`GetByDateRangeAsync(from, to)` keeps `>= from && <= to` (inclusive by contract — document in XML docs).

**Bug to fix in the same pass**: `ExamRepository.GetUpcomingAsync(int days)` applies `.Take(days)` — it treats a *day window* as a *row count*:

```csharp
var today = DateOnly.FromDateTime(timeProvider.GetLocalNow().Date);
var until = today.AddDays(days);
... .Where(e => e.ExamDate >= today && e.ExamDate <= until).OrderBy(e => e.ExamDate) ...
```

**Cross-cutting**: replace every `DateTime.Today`/`DateTime.Now` in module code with an injected `TimeProvider` (registered as `TimeProvider.System` in both hosts). This makes all date math deterministically testable. Done in Slice 0/1, applied from then on.

**Rationale**: FR-P3 demands components live in module projects and are consumed unchanged by both hosts; duplicating the shell would violate that *and* double-maintain ~850 lines of CSS. Storage is a provider-agnostic persistence leaf with no Razor SDK. A `Settings` module is the exact DayDash analogue of MiniMate's `Profile` module and gives the language switch (FR-L2/L3) a home.

**Static assets are shared, not copied.** `daydash-globals.css`, `app.css` and the placeholder logo ship from the RCL's `wwwroot/` and are referenced from **both** hosts' `index.html` as `_content/DayDash.Modules.Settings/css/daydash-globals.css`. Bootstrap stays per host.

**No `culture.js` JS round-trip.** DayDash replaces MiniMate's `blazorCulture.get/set` -> `DotNet.invokeMethodAsync(...)` -> non-DI `MauiPreferencesService` chain with a plain `IAppPreferences`: MAUI over `Microsoft.Maui.Storage.Preferences` (synchronous, no JS hop); Web over `localStorage` with a 6-line shim.

**Feature settings stay in their owning modules.** `SettingsComponent` is a hub of `<NavLink>`s to `settings/event-types`, `settings/subjects`, `settings/reminders` plus inline `<LanguageSelectorComponent />` and `<ThemeToggle />`. Settings depends on nothing.

**`CultureAwareComponentBase`** — the one improvement over MiniMate (whose `NavMenu`/`MainLayout` do *not* subscribe, failing FR-L3):

```csharp
public abstract class CultureAwareComponentBase : ComponentBase, IDisposable
{
    [Inject] protected CultureStateService CultureState { get; set; } = null!;
    protected override void OnInitialized()
    {
        base.OnInitialized();
        CultureState.CultureChanged += OnCultureChanged;
    }
    private void OnCultureChanged(object? sender, CultureInfo culture) => InvokeAsync(StateHasChanged);
    public virtual void Dispose() => CultureState.CultureChanged -= OnCultureChanged;
}
```

Every component that renders a localized string derives from it — including `MainLayout` (`CultureAwareLayoutComponentBase`) and `NavMenu`.

### AD-7 — `.ics` via share sheet; widget refresh via a Storage-owned `IDataChangeHandler` fan-out

**`.ics` delivery — share sheet.** `IcsExportService` splits into a pure `IcsBuilder.Build(IEnumerable<CalendarEvent>) -> string` + the file write. Calendar UI calls the platform-agnostic `IFileShareService`:
- MAUI `MauiFileShareService`: write to `Path.Combine(FileSystem.CacheDirectory, $"DayDash-{yyyyMMdd-HHmmss}.ics")`, then `Share.Default.RequestAsync(new ShareFileRequest { ... })`.
- Web `BrowserDownloadService`: `URL.createObjectURL` + synthetic `<a download>`.

`Share` needs no storage permission on any API level; the child hands the file to Drive/Gmail/Files in one tap; the Web preview gets a real download.

**Widget refresh + reminder rescheduling — one notification bus in Storage:**

```csharp
// Storage/Application/Contracts/DataChange.cs
public enum DataChangeKind { CalendarEventSaved, CalendarEventDeleted, ExamSaved, ExamDeleted,
                             EventTypeChanged, SubjectConfigChanged, ReminderConfigChanged }
public readonly record struct DataChange(DataChangeKind Kind, Guid EntityId);
public interface IDataChangeHandler { Task HandleAsync(DataChange change, CancellationToken ct = default); }
public interface IDataChangeNotifier { Task NotifyAsync(DataChange change, CancellationToken ct = default); }
```

`DataChangeNotifier(IEnumerable<IDataChangeHandler> handlers, ILogger<...>)` fans out, each handler in try/catch + log. `CalendarService`/`StudyPlannerService` call `NotifyAsync` after every write. Handlers:

| Handler | Registered by | Reacts to |
|---|---|---|
| `ReminderRescheduleHandler` | `AddDayDashReminder()` | exam/event saved or deleted, config changed -> cancel + reschedule (FR-R6) |
| `CalendarExamLinkHandler` | `AddDayDashCalendar()` | `ExamDeleted` -> clear `CalendarEvent.LinkedExamId` |
| `AndroidWidgetRefreshHandler` | `DayDash.Maui` host | any change -> broadcast widget update (FR-W4) |

Modules stay interface-only coupled; `DayDash.Web` registers no handlers. The Android handler broadcasts per provider type via `AppWidgetManager.GetAppWidgetIds` + `SendBroadcast(ActionAppwidgetUpdate)`.

## 5. Risks & Mitigations

| # | Risk | Impact | Mitigation |
|---|---|---|---|
| R1 | **ML Kit binding** drags in a large Play Services graph; +10–20 MB APK; restore can fail behind a proxy; surfaces Java `Task`. | Slice 4 blocked | Add the package **first** in Slice 4, prove `dotnet build -f net10.0-android` before any OCR code. Ship the `MlKitTaskCompletionListener` bridge. R8/shrinking Release-only. `<meta-data ... DEPENDENCIES="ocr" />` bundles the model. Fallback: keep parser + edit UI, mark FR-M2 blocked, manual goal entry; rest of Slice 4 still ships. |
| R2 | **`Plugin.LocalNotification`** may lag .NET 10 MAUI; Android 12+ exact-alarm / 13+ `POST_NOTIFICATIONS` gates. | Silent no-fire | Verify `net10.0-android` support before coding. Manifest perms already present — add the **runtime** request + localized denial path. All scheduling behind `INotificationScheduler` (plugin swap = one adapter file). Manual `dumpsys notification` check mandatory. |
| R3 | **Widget `DbContext` outside DI**: no provider in `BroadcastReceiver`; missing DB file; SQLite lock; 10 s ANR budget. | Widget crash / empty | Single `WidgetHost`; `Mode=ReadOnly`; every read try/catch -> localized empty state; never `Migrate()`; dispose within `OnUpdate`; `AsNoTracking()` + bounded (one month max). |
| R4 | **`DateOnly`/`TimeOnly` on SQLite**: member access may not translate; TEXT comparison depends on storage format. | Silent wrong results | AD-2: half-open ranges only, no member access in `Where`. `DateOnlyTimeOnlyRoundTripTests` against real SQLite `:memory:` (EF InMemory would mask a translation failure). No value converters. |
| R5 | **MAUI router switch** (AD-4): no native back button, no per-page lifecycle, WebView startup cost at launch. | Shell-level regression | Do it in Slice 0 where nothing else moves; verify device navigation immediately. Handle hardware back in `MainActivity.OnBackPressed` -> `NavigationManager`. Deleted `*Page.xaml` stay in git history for rollback. |
| R6 | **Test project cannot reference `DayDash.Maui`** (`net10.0-android`). | Platform code untested | AD-5: push all logic into module services. Every MAUI class must be a <=30-line adapter — **explicit code-review criterion**. Platform behaviour covered by scripted device smoke tests. |
| R7 | **bUnit / xunit on .NET 10** compatibility matrix (bUnit 1.40 targets net8/9; xunit v2 vs v3 vs bUnit 2 preview). | Slice 0 blocked | Prove the package combo in Slice 0 with **one** trivial bUnit test first. Fallback order: (1) xunit 2.9 + bunit 1.40; (2) xunit.v3 + bunit 2.x preview; (3) drop bUnit, test code-behinds as plain classes. Never block a slice on bUnit — logic tests carry coverage. |
| R8 | **CPM + `Directory.Build.props` at repo root** can perturb the MAUI workload build. | Build breaks | Keep root props to five properties; convert to CPM and run the **android** build immediately. If MAUI misbehaves, scope `Directory.Build.props` to `src/Modules/` + `tests/` and leave `DayDash.Maui` alone. |
| R9 | **NU1903 may not be clearable** if `SQLitePCLRaw` 2.1.12 is not restorable (only 2.1.11 cached; needs network). | Warning baseline can't reach zero | AD-6 re-scoping removes it from 5 of 7 projects regardless. Remaining exposure documented with the advisory URL + scoped `NoWarn` in exactly two csproj. Re-check on every bump. |
| R10 | **Startup migration failure on an existing device DB**. | Data loss if handled naively | Never `EnsureDeleted`. `MauiProgram` catches, logs, stores the exception in `StartupDiagnostics`; `MainLayout` renders a localized error banner. Keep `--idempotent` scripts for manual recovery. |
| R11 | **`de-CH` vs `de` fallback**: MiniMate uses `"de"`; DayDash requires `de-CH`; neutral resx must resolve from `de-CH`. | Missing translations at runtime | Neutral resx = German with `<NeutralResourcesLanguage>de-CH</NeutralResourcesLanguage>`; only `en` ships as a satellite. `CultureStartupTests` asserts `de-CH` -> neutral, `en` -> satellite. `BlazorWebAssemblyLoadAllGlobalizationData=true` in Web. |
