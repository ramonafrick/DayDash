# Dokumentation: DayDash Full Feature Build-out (Slices 0–7)

**Datum**: 2026-08-31
**Branch**: `feature/full-buildout`
**Plattform**: MAUI (Blazor Hybrid, Android) und Blazor Web (WASM-Vorschau) – dieselben Razor-Komponenten in beiden Hosts
**Module**: Storage, Settings (neu), Calendar, StudyPlanner, Camera, Reminder, Widget
**Grundlage**: `docs/20260830_Requirement.md`, `docs/20260830_plan.md` (Architekturentscheidungen AD-1…AD-9, Risiken R1…R11)

---

## Zusammenfassung

Der Build-out überführt die bis dahin nur kompilierende Skelett-Lösung in sieben funktionierende,
offline lauffähige, vollständig lokalisierte Module. Kern ist eine echte, migrierte und geseedete
SQLite-Datenbank über einen geteilten `DayDashDbContext`, der ohne Verweis auf die Feature-Module
auskommt. Darüber hinaus entstehen: ein neues Modul `DayDash.Modules.Settings` mit der geteilten
Shell und dem Live-Sprachwechsel, echter Kalender mit `.ics`-Export, Lernplaner mit
Prüfungs-Assistent, ML-Kit-OCR für Lernziele, Android-Benachrichtigungen mit Reschedule-Logik,
drei Home-Screen-Widgets, die ohne laufenden App-Prozess direkt aus der DB-Datei lesen, sowie ein
Testprojekt mit 182 grünen xUnit-/bUnit-Tests.

## Architektur-Überblick

### Modul-Graph

```
Storage (Leaf, EF Core ohne Provider)        Settings (Leaf, Kultur + geteilte Shell)
   ^   ^   ^                                     ^    ^    ^    ^    ^
   |   |   |                                     |    |    |    |    |
 Calendar  StudyPlanner  <----------------  Calendar StudyPlanner Camera Reminder Widget
   ^  ^        ^  ^
   |  |        |  +----> Camera        (Camera -> StudyPlanner: LearningGoal, IStudyPlannerService)
   |  +--------+-------> Reminder      (Reminder -> Calendar + StudyPlanner: Termin-/Prüfungstexte)
   +-----------+-------> Widget        (Widget -> Calendar + StudyPlanner: Lesemodell)

DayDash.Migrations (net10.0)  -> Storage, Calendar, StudyPlanner, Reminder  + EFCore.Sqlite/.Design
tests/DayDash.Tests (net10.0) -> alle 7 Module + DayDash.Migrations         + xunit, bunit, EFCore.Sqlite/InMemory

                                 + Xamarin.Google.MLKit.TextRecognition + Plugin.LocalNotification
```

Kopplung ausschliesslich über Interfaces, Domain-Entities, reine Builder-Klassen und den geteilten
`DayDashDbContext`. Kein Modul referenziert die konkreten Typen eines anderen Feature-Moduls.
`Storage` und `Settings` sind Blätter ohne `ProjectReference` auf andere Module.

### Kernentscheidungen

**`IModelConfiguration` per DI statt Circular Dependency (AD-1).**
`DayDashDbContext` trägt keine `DbSet`-Properties und kein festes `OnModelCreating`. Der Ctor nimmt
`IEnumerable<IModelConfiguration>` entgegen und ruft in `OnModelCreating` jede Contribution auf.
Jedes entity-besitzende Modul liefert genau eine `IModelConfiguration` in
`Infrastructure/Persistence/`, die idiomatische `IEntityTypeConfiguration<T>`-Klassen anwendet.
`AddDbContext<T>` löst zusätzliche Ctor-Parameter aus dem Container auf, der DI-Pfad braucht also
keine Sonderverdrahtung. Entities werden über `context.Set<T>()` erreicht.
Verworfen: `IEnumerable<IEntityTypeConfiguration<T>>` direkt injizieren – DI kann keine
offen-generische Collection auflösen, deren `T` an der Injektionsstelle unbekannt ist.

**Eigenes Projekt `DayDash.Migrations` (AD-1).**
Ein Model-Snapshot in `Storage` würde brechen, sobald irgendein Modul eine Enum oder ein
modul-eigenes Value Object hinzufügt. Die Migrationen (`InitialCreate`, `EventReminderLeadTime`)
plus Snapshot liegen deshalb in einem dedizierten `net10.0`-Projekt, das nur `Storage` und die drei
entity-besitzenden Module referenziert. Es enthält:
`DayDashModelConfigurations.All` (feste Reihenfolge Calendar, StudyPlanner, Reminder),
`DayDashDbContextFactory.CreateSqlite(path, readOnly)` für die beiden Nicht-DI-Konstruktionspfade
(Design-Time-Tooling, Android-Widget), `DayDashDesignTimeDbContextFactory : IDesignTimeDbContextFactory<>`
und `DayDashSqliteStorageExtensions.AddDayDashSqliteStorage(path)`, das die Migrations-Assembly
hartkodiert. `Storage` selbst nennt nie einen Provider und referenziert nur
`Microsoft.EntityFrameworkCore` (ohne SQLite). Damit verschwindet der verwundbare native
SQLite-Binary (NU1903, GHSA-2m69-gcr7-jv3q) aus allen fünf Feature-RCLs.

**Daten-Änderungs-Bus in Storage (AD-7).**
`DataChange(DataChangeKind Kind, Guid EntityId)` wird nach jedem Write über
`IDataChangeNotifier.NotifyAsync` an alle registrierten `IDataChangeHandler` gefächert; jeder
Handler läuft in try/catch, ein Fehler wird geloggt und geschluckt, damit er den auslösenden Write
nie bricht. Handler:

| Handler | Registriert von | Reagiert auf |
|---|---|---|
| `ReminderRescheduleHandler` | `AddDayDashReminder()` | jede Änderung ausser `EventTypeChanged` -> `RescheduleAllAsync` |
| `CalendarExamLinkHandler` | `AddDayDashCalendar()` | `ExamDeleted` -> `CalendarEvent.LinkedExamId` löschen |
| `AndroidWidgetRefreshHandler` | `DayDash.Maui` (Host) | Event-/Exam-Änderungen -> `APPWIDGET_UPDATE` broadcasten |

`DayDash.Web` registriert keine Handler. Module bleiben interface-only gekoppelt.

**Ein `BlazorWebView` statt nativer Shell (AD-4).**
`AppShell.xaml` und alle `*Page.xaml` sind gelöscht. `MainPage.xaml` hostet einen einzigen
`BlazorWebView` mit `Components/Routes.razor` (`<Router>` + `AdditionalAssemblies` für alle Module,
`DefaultLayout = MainLayout` aus der Settings-RCL, expliziter `<NotFound>`). Beide Hosts tragen
dünne `@page`-Wrapper (~6–25 Zeilen), die Titel injizieren und die Modul-Komponente einbetten;
die Modul-Komponenten selbst sind route-agnostisch. Damit gibt es eine Shell, ein
Navigationsmodell und `DayDash.Web` ist eine echte Vorschau der realen App.

**Live-i18n über `CultureStateService` (AD-3).**
Singleton in `Settings`; `ChangeCulture` setzt alle vier `CultureInfo`-Statics und feuert
`CultureChanged`. `CultureAwareComponentBase` / `CultureAwareLayoutComponentBase` abonnieren im
`OnInitialized` und rufen `InvokeAsync(StateHasChanged)`; jede Komponente mit lokalisiertem Text
leitet davon ab, auch `MainLayout` und `NavMenu`. Kein JS-Roundtrip: `IAppPreferences` ist im MAUI
synchron über `Microsoft.Maui.Storage.Preferences`, im Web über `localStorage`. Default-Kultur
`de-CH` als neutrale resx (`NeutralResourcesLanguage` in `Directory.Build.props`), einziger
Satellit `en`. Auflösung tolerant: `SupportedCultures.Normalize` bildet `de*`/leer/Unfug auf
`de-CH` ab, `en*` auf `en`.

**`DateOnly`/`TimeOnly` nativ, Datumsfilter halboffen (AD-2).**
Keine `ValueConverter`. EF Core 10 mappt `DateOnly`/`TimeOnly` auf `TEXT` und vergleicht sie
lexikografisch korrekt. Jeder Datumsfilter ist ein halboffener Bereich
(`>= first && < next`), kein Member-Zugriff (`.Year`, `.Month`) in `Where`. Zeitquelle überall
`TimeProvider` (Host: `TimeProvider.System`, Tests: `FakeTimeProvider`).

**Cross-Modul-Komposition am Host-Page, nicht per `ProjectReference` (AD-9).**
`Calendar.EventEditComponent` exponiert `RenderFragment<ExamAssistantRequest> ExamAssistantTemplate`
und `EventCallback<Guid> OnOpenLinkedExam`. `Pages/Calendar.razor` in beiden Hosts füttert
StudyPlanners `<ExamAssistantComponent>` als Template ein und navigiert bei `OnOpenLinkedExam` zu
`/study/exams/{id}`. Prüfungserkennung sprachunabhängig über `EventTypeConfig.Key == "exam"`, nur
`Name` ist lokalisiert/umbenennbar. Ausnahme: `Reminder` referenziert `Calendar` und `StudyPlanner`
direkt (Consumer-only, kein Zyklus), weil es beide Entities für den Benachrichtigungstext braucht.

## Modul: Storage (FR-S1…S6)

**Zweck**: geteilte Persistenz für alle Module; provider-agnostisch.

### Hauptkomponenten

- **`DayDashDbContext`** – `DbSet`-frei, Modell aus `IModelConfiguration`-Contributions (AD-1).
- **`StorageModuleExtensions.AddDayDashStorage(Action<DbContextOptionsBuilder>)`** – registriert den
  Context, `IRepository<>` -> `BaseRepository<>`, `IDatabaseInitializer` -> `DatabaseInitializer`,
  `IDataChangeNotifier` -> `DataChangeNotifier` (alle scoped). Der Provider kommt vom Host:
  MAUI ruft `AddDayDashSqliteStorage(path)` (aus `DayDash.Migrations`), Web ruft direkt
  `AddDayDashStorage(o => o.UseInMemoryDatabase("DayDash-Preview"))`.
- **`DatabaseInitializer`** – `MigrateAsync()` bei relationalen Providern, `EnsureCreatedAsync()`
  bei InMemory; danach alle `IDataSeeder` nach `Order` sortiert. Ein Seeder-Fehler wird geloggt und
  weitergeworfen (Host fängt ihn, siehe unten).
- **`IDataSeeder`** – je Modul einer, idempotent (`if (await Set<T>().AnyAsync()) return;`):
  `EventTypeSeeder` (Order 10), `SubjectConfigSeeder` (20), `ReminderConfigSeeder` (30).
- **`BaseRepository<T>`** – `GetByIdAsync`/`GetAllAsync`/`Add`/`Update`/`Delete`; exponiert
  `DbContext Context`, damit Feature-Services für Mehr-Entity-Operationen direkt am `DbSet` arbeiten.
- **`DayDashDatabase.FileName`** = `"DayDash.db"`.
- **Daten-Änderungs-Bus** – `DataChange`, `IDataChangeHandler`, `IDataChangeNotifier`,
  `DataChangeNotifier` (siehe AD-7).

### Ablauf: Start

Host baut den Container, öffnet einen Scope, ruft `IDatabaseInitializer.InitializeAsync()`.
Bei Fehler wird die Exception in `StartupState.DatabaseError` abgelegt (nie `EnsureDeleted`,
keine stille Datenlöschung, R10); `MainLayout` zeigt daraufhin ein lokalisiertes Fehlerbanner.

### Datenmodell

Sechs Tabellen, angelegt durch Migration `InitialCreate` (`20260831041211`):
`EventTypeConfigs`, `Exams`, `ReminderConfigs`, `SubjectConfigs`, `CalendarEvents`, `LearningGoals`.
Details siehe Abschnitt „Datenbank / Storage".

### Lokalisierung

Keine eigenen Strings (Storage hat kein UI). Default-Namen der geseedeten Event-Typen/Fächer
kommen einmalig aus `CalendarResources` / `StudyPlannerResources` und leben danach als Nutzerdaten.

## Modul: Settings (neu) (FR-L1…L4, FR-P2, FR-P3)

**Zweck**: zweites Blatt neben Storage. Trägt die app-weite Kultur, die geteilte MiniMate-Shell und
die Einstellungs-Landingpage. Jedes UI-Modul referenziert Settings.

### Hauptkomponenten

- **`CultureStateService`** (Singleton) – Owner der aktuellen `CultureInfo`, Event `CultureChanged`,
  setzt alle vier `CultureInfo`-Statics; No-op bei gleichem Namen; `ChangeCulture(string)` geht über
  `SupportedCultures.Resolve`.
- **`SupportedCultures`** – `Default = "de-CH"`, `English = "en"`, `Normalize`/`Resolve`.
- **`CultureAwareComponentBase` / `CultureAwareLayoutComponentBase`** – Abonnement + Re-Render +
  `Dispose`; `CultureChangeSubscription` kapselt Sub/Unsub einmalig.
- **`IAppPreferences`** – `Task<string?> GetAsync(key)` / `Task SetAsync(key, value)`; Host-Adapter
  `MauiAppPreferences` (synchron über `Preferences`), `LocalStorageAppPreferences` (Web).
- **`IFileShareService`** – `ShareFileAsync(path, title)`; Host-Adapter `MauiFileShareService`
  (`Share.Default.RequestAsync`), `BrowserDownloadService` (`URL.createObjectURL` + `<a download>`).
- **`StartupState`** (Singleton) – hält `DatabaseError` für das Fehlerbanner.
- **UI**: `MainLayout` + `NavMenu` + `ThemeToggle` (aus MiniMate portiert, jetzt kultur-abonnierend),
  `LanguageSelectorComponent`, `SettingsComponent` (Hub mit `<NavLink>`s auf
  `settings/event-types`, `settings/subjects`, `settings/reminders` plus Sprache und Theme),
  `NotFoundContent`.
- **Statische Assets**: `_content/DayDash.Modules.Settings/css/{app.css, daydash-globals.css}`,
  `_content/DayDash.Modules.Settings/img/daydash-logo.svg` – aus der RCL, von beiden Hosts referenziert.

### Ablauf: Sprachwechsel (live, ohne Neustart)

`LanguageSelectorComponent.OnLanguageChangedAsync` -> `IAppPreferences.SetAsync("BlazorCulture", …)`
-> `CultureStateService.ChangeCulture(name)` -> `CultureChanged` -> jede
`CultureAwareComponentBase`-Ableitung re-rendert. Formularwerte bleiben erhalten (nur die Labels
rendern neu), da nur `StateHasChanged` läuft, keine Navigation.

### Ablauf: Kultur beim Start

MAUI setzt die Kultur im `App`-Ctor **vor** dem ersten Render aus
`Preferences.Get("BlazorCulture", "de-CH")`. Web setzt sie in `Program.cs` nach dem Build aus
`IAppPreferences` (async, `localStorage`). `DayDash.Web.csproj` trägt
`BlazorWebAssemblyLoadAllGlobalizationData=true`.

### Lokalisierung

`NavigationResources` (`BrandName`, `Calendar`, `StudyPlan`, `Camera`, `Settings`,
`ToggleNavigation`, `NotFoundTitle`, `NotFoundMessage`) und
`SettingsResources` (`PageTitle`, `SettingsTitle`, `Language`, `LanguageGerman`, `LanguageEnglish`,
`Appearance`, `ThemeLight`, `ThemeDark`, `EventTypeSettings`, `SubjectSettings`, `ReminderSettings`,
`Save`, `Saved`, `Cancel`, `DatabaseErrorTitle`, `DatabaseErrorMessage`, `LanguageChanged`,
`PreviewOnly`, `NotAvailableInBrowser` u. a.), jeweils neutral (de-CH) + `.en`.

## Modul: Calendar (FR-C1…C7)

**Zweck**: Monats-/Wochenkalender über echte Daten, Ereignis-CRUD, Event-Typ-Verwaltung,
`.ics`-Export, Übergabe an den Prüfungs-Assistenten.

### Hauptkomponenten

- **`CalendarGridBuilder`** (reine statische Klasse) – `Build(year, month, firstDayOfWeek, today,
  events, eventTypes) -> IReadOnlyList<CalendarWeek>`; immer 6×7, führende/nachlaufende Tage mit
  `IsCurrentMonth = false`, `IsToday` nur bei `date == today`, `DotColors` pro Tag distinct nach
  Event-Typ-Farbe (null-`EventTypeId` -> kein Punkt, kein Crash).
- **`IcsBuilder`** (rein) – `Build(events, generatedAt) -> string`. RFC 5545: `DTSTAMP` aus
  `generatedAt` (UTC), `VALUE=DATE` bei `IsAllDay` (`DTEND` = Folgetag), sonst `DTSTART`/`DTEND`
  mit Fallback `TimeFrom ?? 00:00` bzw. `TimeTo ?? 23:59:59`; Escaping von `\ ; ,` und Zeilenumbruch;
  Folding bei 75 UTF-8-Oktetten ohne Surrogatpaar-Split; `DESCRIPTION` nur bei nicht-leeren Notes.
- **`CalendarService`** – `GetEventsFor{Month,Week,Day}Async`, `GetEventsInRangeAsync`
  (inklusiv per Kontrakt), `GetEventAsync`, `CreateEventAsync`/`UpdateEventAsync`/`DeleteEventAsync`
  (jeweils genau eine `DataChange`), `GetEventTypesAsync`, `SaveEventTypeAsync` (Rename ändert nie
  `Key`/`IsDefault`), `DeleteEventTypeAsync` (Default-Typen nicht löschbar; FK `SetNull` lässt
  Events stehen), `ExportIcsAsync`.
- **`CalendarRepository`** – halboffene Bereichsabfragen (AD-2).
- **`CalendarExamLinkHandler : IDataChangeHandler`** – bei `ExamDeleted` `LinkedExamId` der
  betroffenen Events auf null.
- **UI**: `CalendarComponent` (Shell: Monats-/Wochen-Toggle, „Neues Ereignis", `.ics`-Export-Button,
  Toast; hält die Panels Detail/Edit/ExamAssistant), `CalendarMonthView`, `CalendarWeekView`,
  `EventEditComponent` (`EditForm` + Validierung, detachte Kopie beim Speichern),
  `EventDetailComponent`, `EventListComponent`, `EventTypeSettingsComponent`, `DeleteConfirmDialog`.

### Ablauf: Prüfungs-Ereignis -> Exam-Assistent -> `LinkedExamId` (FR-C6)

1. In `EventEditComponent` speichert der Nutzer ein Ereignis mit Typ `Key == "exam"` ohne
   `LinkedExamId`.
2. `CalendarComponent.SaveAsync` persistiert das Ereignis und schaltet auf `Panel.ExamAssistant`,
   erzeugt `ExamAssistantRequest(Title, Date)`.
3. Das vom Host per `ExamAssistantTemplate` eingebettete `ExamAssistantComponent` (StudyPlanner)
   läuft; bei Abschluss ruft der Host `_calendar.CompleteExamLinkAsync(examId)`, was
   `LinkedExamId` setzt und das Ereignis erneut speichert. Bei Abbruch:
   `_calendar.CancelExamLink()` – kein verwaistes Exam, das Ereignis bleibt.
4. Öffnen eines Prüfungs-Ereignisses ruft `OnOpenLinkedExam` -> Host navigiert zu
   `/study/exams/{id}`.

### Ablauf: `.ics`-Export (FR-C7)

`CalendarComponent.ExportAsync` schreibt `IcsBuilder`-Output in eine temporäre Datei
(`DayDash-<yyyyMMdd-HHmmss>.ics`) und übergibt sie an `IFileShareService`: MAUI öffnet das
Share-Sheet, Web löst einen Download aus. `Share` braucht auf keiner API-Ebene eine
Speicherberechtigung.

### Datenmodell

`CalendarEvent` (`Id`, `Title`, `EventTypeId : Guid?` FK `SetNull` auf `EventTypeConfig`, `Date`,
`TimeFrom`/`TimeTo : TimeOnly?`, `Notes`, `IsAllDay`, `ReminderDaysBefore : int?`,
`LinkedExamId : Guid?`). `EventTypeConfig` (`Id`, `Key`, `Name`, `Color`, `IsDefault`); sechs
Defaults mit festen Guids und Farben (`exam`, `homework`, `holidays`, `birthday`, `appointment`,
`other`). Indizes auf `Date`, `EventTypeId`, `LinkedExamId`; gefilterter Unique-Index auf
`Key <> ''`.

### Lokalisierung

`CalendarResources` (+ `.en`): u. a. `MonthView`, `WeekView`, `NewEvent`, `EditEvent`,
`EventTitle`, `EventType`, `AllDay`, `TimeFrom`, `TimeTo`, `NoEvents`, `NoEventsThisWeek`,
`ConfirmDeleteEvent`, `ExportIcs`, `ExportSuccess`, `ExportFailed`, `OpenLinkedExam`,
`AlsoDeleteLinkedExam`, `TitleRequired`, `TimeToBeforeTimeFrom`, `Weekday_Mon`…`Weekday_Sun`,
`EventTypeInUse`, `DefaultEventType_Exam/_Homework/_Holidays/_Birthday/_Appointment/_Other`.

## Modul: StudyPlanner (FR-X1…X7)

**Zweck**: Prüfungs-CRUD mit Lernzielen, Live-Empfehlung aus **persistierter** `SubjectConfig`,
berechnete `RecommendedMinutes`/`DailyMinutes`, Fach-Einstellungen, Heute-Ansicht,
Prüfungs-Assistent.

### Hauptkomponenten

- **`StudyMath`** (rein) – `RecommendedMinutes(goalCount, minutesPerGoal)` = `max(g,0) * max(m,0)`;
  `DailyMinutes(total, examDate, today)` = `max(total,0) / max(examDate - today, 1)` (kein
  Div-by-zero, Vergangenheit auf 1 geklemmt); `DaysRemaining`.
- **`SubjectConfigService`** – `GetAllAsync`, `GetMinutesPerGoalAsync(name)` (Fallback
  `SubjectConfig.DefaultMinutesPerGoal = 15`), `SaveAsync`/`DeleteAsync` (jeweils
  `SubjectConfigChanged`-`DataChange`).
- **`StudyPlannerService`** – `CreateExamAsync`/`UpdateExamAsync` berechnen
  `RecommendedMinutes` + `DailyMinutes` vor jedem Save (auch bei Edits) und feuern `ExamSaved`;
  `UpdateExamAsync` reconciled die Lernzielliste direkt am `DbSet<LearningGoal>` (entfernen /
  per Id aktualisieren / neu anlegen, `SortOrder` = Index); `SaveLearningGoalsAsync` ersetzt alle
  Ziele eines Exams vollständig (neue Guids, um Kollision mit soeben gelöschten Zeilen zu
  vermeiden); `SetGoalCheckedAsync` persistiert sofort; `GetTodayStudyPlanAsync` liefert Exams mit
  `DailyMinutes > 0 && ExamDate >= today`.
- **`ExamRepository`** – `AsNoTracking` + `Include(LearningGoals.OrderBy(SortOrder))`;
  `GetUpcomingAsync(days)` als echtes Tagesfenster (`ExamDate >= today && <= today+days`), nicht
  `.Take(days)`; `GetWithGoalsAsync` tracked für Updates.
- **UI**: `ExamListComponent`, `ExamCreateComponent` (Validierung, `UpdateRecommendation` an
  `@bind-Value:after`), `ExamDetailComponent` (`[Parameter] Guid ExamId`, lädt das Exam,
  Checkbox-Toggle persistiert sofort), `ExamAssistantComponent` (3 Schritte, nimmt `InitialTitle` /
  `InitialDate` als Primitive – **kein** Verweis auf Calendar; `EventCallback<Guid> OnExamCreated`,
  `EventCallback OnCancel`), `SubjectConfigComponent`, `TodayStudyPlanComponent` (pro Exam Fach +
  Minuten und die Tagessumme).

### Datenmodell

`Exam` (`Id`, `Title`, `Subject` als String – kein FK, damit gelöschte Fächer die Prüfung nicht
kaputtmachen, `ExamDate`, `TotalStudyMinutes`, `RecommendedMinutes`, `DailyMinutes`,
`List<LearningGoal>`). `LearningGoal` (`Id`, `ExamId` FK Cascade, `Text`, `IsChecked`, `SortOrder`).
`SubjectConfig` (`Id`, `Name`, `MinutesPerGoal` – DB-Default 15); fünf Defaults mit festen Guids
(Mathematik, Deutsch, NMG, Englisch, Französisch). Indizes: `Exams.ExamDate`,
`LearningGoals (ExamId, SortOrder)`.

### Lokalisierung

`StudyPlannerResources` (+ `.en`): u. a. `MinutesPerGoal`, `NewSubject`, `StudyPlanTitle`,
`NewExam`, `EditExam`, `ConfirmDeleteExam`, `AddGoal`, `GoalText`, `TotalMinutesToday`,
`NoStudyToday`, `ExamAssistant`, `StepSubject`/`StepGoals`/`StepMinutes`, `Next`/`Back`/`Finish`,
`SubjectRequired`, `MinutesRange`, `Overdue`, `TodayLabel`/`TomorrowLabel`,
`SubjectDeletedFallback`, `SaveFailed`, `DefaultSubject_Math/_German/_Nmg/_English/_French`.

## Modul: Camera / OCR (FR-M1…M5)

**Zweck**: Foto einer Lernziel-Liste -> ML-Kit-OCR offline -> editierbare, an ein Exam gebundene
`LearningGoal`s.

### Hauptkomponenten

- **`ICameraService.CaptureAndRecognizeTextAsync() -> Task<OcrResult>`** – wirft nie.
- **`OcrResult`** = `enum OcrCaptureStatus { Success, NoTextFound, Cancelled, PermissionDenied,
  NotSupported, Failed }` + `record OcrResult(Status, Text)` mit `Success(text)` / `Failure(status)`.
- **`LearningGoalParser`** (rein, `ILearningGoalParser`) – Split an `\n`/`\r`, interne
  Whitespace-Runs zu einem Space, trimmen, Leerzeilen ohne `SortOrder`-Lücken verwerfen, Cap bei
  200 Zeichen ohne Surrogatpaar-Split; `IsChecked = false`, `SortOrder` = laufender Index,
  `ExamId` gesetzt.
- **UI**: `CameraCaptureComponent` (Exam-Auswahl bzw. `[Parameter] Guid? ExamId`, Fächer-/Exam-Liste
  beim Init, pro Status eine lokalisierte Meldung, `Success` mit 0 geparsten Zeilen ->
  `NoTextFound`), `LearningGoalEditComponent` (hinzufügen/löschen/umbenennen/verschieben,
  kontinuierliche Neunummerierung), Persistenz über `IStudyPlannerService.SaveLearningGoalsAsync`.

### Ablauf: OCR (nur Android real)

`MediaPicker.CapturePhotoAsync` -> `InputImage.FromFilePath` (liest EXIF-Orientierung) ->
`TextRecognition.GetClient(DefaultOptions).Process(image)` -> die Java-`Task` wird über
`MlKitTaskCompletionListener : IOnCompleteListener` (Bridge auf `TaskCompletionSource`) awaitbar
gemacht -> `Text.GetText()`. Recognition läuft bewusst zu Ende (kein Abbruch, sonst würde der
Recognizer disposed, während ML Kit ihn nativ noch nutzt). Jeder Fehlerpfad
(`PermissionException`, `FeatureNotSupportedException`, `photo == null`, `OperationCanceledException`,
sonstige `Exception`) mappt auf einen Status. Das ML-Kit-Modell liegt im APK
(`AndroidManifest.xml`: `<meta-data com.google.mlkit.vision.DEPENDENCIES = "ocr" />`).
`WebCameraService` liefert `OcrResult.Failure(NotSupported)`.

### Datenmodell

Nicht betroffen – schreibt `LearningGoal`s über StudyPlanner.

### Lokalisierung

`CameraResources` (+ `.en`): u. a. `CameraTitle`, `Recognizing`, `NothingRecognized`,
`CameraNotAvailable`, `PermissionDenied`, `CaptureCancelled`, `RecognitionFailed`, `Retake`,
`SelectExam`, `NoExamSelected`, `AttachToExam`, `GoalsSaved`, `GoalsSaveFailed`.

## Modul: Reminder (FR-R1…R6)

**Zweck**: Android-Benachrichtigungen; bedingte tägliche Lern-Erinnerung, Termin-Erinnerungen,
persistierte Config, korrektes Abbrechen/Neuplanen.

### Hauptkomponenten

- **`INotificationScheduler`** (Plattform-Naht) – `ScheduleAsync(NotificationRequest)`,
  `CancelAsync(id)`, `CancelAllAsync()`, `RequestPermissionAsync()`, `bool IsSupported`.
  `MauiNotificationScheduler` (dünner `Plugin.LocalNotification`-Adapter, legt den
  Android-Channel `daydash_reminders` lazy an, `IsSupported = true`); `NullNotificationScheduler`
  (`TryAddSingleton`-Default, `IsSupported = false`) für Web/Tests.
- **`IReminderService` / `ReminderService`** (Modul-Orchestrator) – `GetConfigAsync`,
  `SaveConfigAsync` (persistiert + `RescheduleAllAsync`), `RescheduleAllAsync`,
  `NotificationsSupported` (spiegelt `scheduler.IsSupported`). Kein persistentes Register: bei jedem
  Reschedule erst `CancelAllAsync`, dann komplett neu aufbauen (FR-R6).
- **`ReminderTextBuilder`** (rein) – lokalisierte Titel/Bodies über `IStringLocalizer<ReminderResources>`;
  `DailyStudyBody` gibt `null` zurück, wenn heute nichts zu lernen ist (Signal für „kein Daily").
- **`NotificationIds`** – deterministisch: `DailyStudyReminder = 1`; `ForExam`/`ForEvent` per FNV-1a
  über alle 16 Guid-Bytes mit Namespace-Salt, `& 0x7FFFFFFF`, Werte < 100 angehoben. Stabil über
  Prozess-Restarts (anders als `GetHashCode`).
- **`ReminderRescheduleHandler : IDataChangeHandler`** – alles ausser `EventTypeChanged` löst
  `RescheduleAllAsync` aus.
- **UI**: `ReminderSettingsComponent` – lädt Config im `OnInitializedAsync`, speichert +
  reschedult; zeigt bei `!NotificationsSupported` den Hinweis „nicht in der Browser-Vorschau".

### Ablauf: `RescheduleAllAsync`

1. Config laden; wenn `!IsEnabled` -> `CancelAllAsync` und fertig.
2. `RequestPermissionAsync` (Android 13+; No-op sonst).
3. **Tägliche Lern-Erinnerung**: `GetTodayStudyPlanAsync`, Summe `DailyMinutes`. Ist `DailyStudyBody`
   `null` -> nichts planen (FR-R2). Sonst als **Einmal-Termin** für das nächste Auftreten der
   konfigurierten Uhrzeit (heute, falls noch in der Zukunft, sonst morgen). Bewusst kein
   `Repeat.Daily`, damit nie mit veraltetem Text weitergefeuert wird; wird bei App-Start
   (`App.OnStart`), Reboot (`BootReceiver`) und jeder `DataChange` neu gesetzt.
4. **Termin-Erinnerungen**: Events im 60-Tage-Fenster; Vorlauf `e.ReminderDaysBefore ?? config.EventReminderDaysBefore`
   (negativ -> überspringen); Uhrzeit `TimeFrom ?? 08:00`, ganztägig -> `08:00`; alles in lokaler
   `DateTime`-Rechnung (DST); `deliverAt <= now` -> überspringen (nie in der Vergangenheit).

### Datenmodell

`ReminderConfig` – Einzelzeile mit fester `SingletonId` (`DailyStudyReminderTime : TimeOnly` = 15:30,
`EventReminderDaysBefore : int` = 1, `IsEnabled : bool` = true). `CalendarEvent.ReminderDaysBefore
: int?` per Migration `EventReminderLeadTime` (`20260831071702`) ergänzt.

### Plattformspezifisch (nur `DayDash.Maui`)

`MauiNotificationScheduler`, `BootReceiver` (`[BroadcastReceiver]`,
`ACTION_BOOT_COMPLETED` + `ACTION_MY_PACKAGE_REPLACED`, `GoAsync()` für den Async-Teil).
`App.OnStart` reschedult per DI-Scope. `builder.UseLocalNotification()` in `MauiProgram`.

### Lokalisierung

`ReminderResources` (+ `.en`): `DailyStudyReminderTitle` („Zeit zum Lernen"),
`DailyStudyReminderBody` (`"Lernen für {0} – {1} Min heute"`),
`DailyStudyReminderBodyMultiple` (`"{0} und {2} weitere – {1} Min heute"`),
`EventReminderTitle` („Bald fällig"), `EventReminderBody` (`"{0} am {1}"`),
`NotificationChannelName`/`-Description`, `DailyStudyReminderTime`, `EventReminderDaysBefore`,
`EnableNotifications`, `NotificationsUnavailable`, `Save`, `Saved`.

## Modul: Widget (FR-W1…W4)

**Zweck**: drei Android-Home-Screen-Widgets (Tag / Woche / Monat), die ohne laufenden App-Prozess
direkt aus der DB-Datei lesen.

### Hauptkomponenten

- **`IWidgetDataService` / `WidgetDataService((DayDashDbContext, TimeProvider))`** – nur
  `AsNoTracking`, halboffene Bereiche, `.Take`-Deckel (`DayListCap = 6`, `WeekListCap = 20`).
  `GetDayAsync` (heutige Events, nächstes Event ab heute, heutige Lern-Slices + Summe),
  `GetWeekAsync` (Montag-Start, `>= weekStart && < weekEnd`), `GetMonthAsync` (nutzt
  `CalendarGridBuilder` für das 6×7-Mini-Grid, `DaysWithEvents` distinct + sortiert). Jedes Snapshot
  hat eine `Empty(...)`-Factory.
- **`WidgetTextFormatter`** (rein) – Snapshot -> lokalisierter RemoteViews-Text; `null`-Snapshot
  (Datenzugriff fehlgeschlagen) -> `WidgetResources.DataUnavailable`. Monat als monospaced
  ASCII-Grid mit Markern (`+` heute+Events, `.` heute, `*` Events).
- **`WidgetResources`** – Hand-Designer mit setzbarer `static Culture` (Widgets haben kein DI,
  kein `IStringLocalizer`).

### Ablauf: Widget-Update

`DayDash{Day,Week,Month}Widget : AppWidgetProvider.OnUpdate` -> `WidgetHost.ApplyCulture()`
(liest `Preferences["BlazorCulture"]`, setzt `WidgetResources.Culture`) ->
`WidgetHost.Read(context, s => s.GetDayAsync())`: DB-Pfad aus `context.FilesDir`, existiert die
Datei nicht -> `default`; sonst read-only Context über
`DayDashDbContextFactory.CreateSqlite(path, readOnly: true)`, `PRAGMA busy_timeout = 3000`, Query
synchron ausgeführt, Context im `using` entsorgt. **Jede** Exception -> `default` -> Formatter
rendert den Leerzustand. RemoteViews werden gefüllt, Tap-`PendingIntent` (`WidgetTapIntent.OpenApp`,
`MainActivity`, `Immutable`) gesetzt, `UpdateAppWidget`.

### Ablauf: Refresh bei Datenänderung (FR-W4)

`AndroidWidgetRefreshHandler : IDataChangeHandler` (im Host registriert) ignoriert
`SubjectConfigChanged`/`ReminderConfigChanged`/`EventTypeChanged` und broadcastet sonst pro
Provider-Typ `ACTION_APPWIDGET_UPDATE` mit den via `GetAppWidgetIds` ermittelten Ids.

### Datenmodell

Nicht betroffen (read-only). Verwendet `CalendarEvent` und `Exam`.

### Lokalisierung

`WidgetResources` (+ `.en`): `DayWidgetTitle`, `WeekWidgetTitle`, `MonthWidgetTitle`, `NextEvent`,
`StudyPlan`, `Minutes`, `NoEventsToday`, `NoEventsThisWeek`, `NoStudyToday`, `AllDay`,
`DataUnavailable`, `Weekday_Mon`…`Weekday_Sun`, `WeekdayHeadings`. Widget-Picker-Labels als
Android-`@string/`-Ressourcen (`values/` + `values-en/`).

### Plattformspezifisch (nur `DayDash.Maui`)

`WidgetHost`, `WidgetTapIntent`, `AndroidWidgetRefreshHandler`, die drei `AppWidgetProvider` samt
Layouts (`Resource.Layout.widget_daydash_*`) und `@xml/daydash_*_widget_info`.

**Migrationen** (in `src/DayDash.Migrations/Migrations/`):

## Nur auf dem Gerät verifizierbar

- **Echte DB-Anlage und Seeding**: `DayDash.db` wird beim ersten Start via
  `MigrateAsync()` angelegt und mit 6/5/1 Zeilen geseedet; erneuter Start dupliziert nichts.
- **`.ics`-Import**: die exportierte Datei muss real in Google Calendar re-importierbar sein
  (Datum/Titel/All-Day korrekt). Der Builder ist getestet, der Share-/Import-Weg nicht.
- **ML-Kit-OCR**: Foto einer gedruckten Liste -> Zeilen als editierbare Ziele -> speichern ->
  nach Force-Stop + Neustart noch vorhanden. Modell-Bundling im APK, EXIF-Orientierung,
  Play-Services-Graph.
- **Notification-Zustellung und Boot-Reschedule**: tägliche Erinnerung feuert zur konfigurierten
  Zeit mit lokalisiertem Text nur bei Lernminuten > 0; nach Reboot (`BootReceiver`) neu gesetzt;
  Löschen von Exam/Event entfernt die zugehörigen Erinnerungen; `POST_NOTIFICATIONS` auf API 33+.
- **Widgets bei totem App-Prozess**: alle drei Widgets zeigen nach `am force-stop` echte Daten aus
  der DB-Datei; fehlende DB-Datei -> lokalisierter Leerzustand, kein Crash, kein ANR;
  paralleler App-Write -> `busy_timeout` statt Leerzustand.
- **Visuelle / Theme-Parität**: identische NavMenu, Tokens, `ThemeToggle`-Position und
  Dark-Mode-Verhalten in beiden Hosts; hardware Back-Button.

## Bekannte Einschränkungen und Platzhalter

- **`daydash-logo.svg`** (`_content/DayDash.Modules.Settings/img/`) ist ein Platzhalter; das finale
  Logo liefert der Nutzer später (Out of Scope laut Requirement).
- Kein persistentes Register geplanter Notification-Ids: `RescheduleAllAsync` cancelt pauschal
  alles und baut neu auf. Robust, aber ein kurzer Moment ohne geplante Erinnerungen.
- Tägliche Lern-Erinnerung als Einmal-Termin statt `Repeat.Daily` – korrekt nur, solange die App
  regelmässig gestartet wird oder ein `DataChange`/Reboot eintritt.
- `DayDash.Web` nutzt EF Core InMemory: Daten sind bei jedem Neuladen weg (gewollt, reine Vorschau).
- Widget-Monatsansicht ist ein monospaced ASCII-Grid (RemoteViews-Textbeschränkung), kein
  gezeichnetes Raster.
- `NU1903`/`NU1608` bleiben in `DayDash.Maui` und `DayDash.Migrations` als akzeptierte Warnungen
  bestehen, bis eine nicht-verwundbare `SQLitePCLRaw`-Version restore-bar ist (R9).
- MAUI zielt nur auf `net10.0-android`; iOS/macOS/Windows sind Out of Scope.
